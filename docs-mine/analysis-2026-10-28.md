# Анализ проекта и план действий

Дата: 28 октября 2026 года.

## Область проверки и ограничения

Проверены структура репозитория, Compose/Swarm, основные скрипты обновления,
DNS-цепочка, HTTPS-прокси, dashboard, Telegram-бот и dns-guard.
Это анализ исходников, а не аудит работающего сервера. Локальные env/override-файлы,
правила firewall и фактическая конфигурация контейнеров могут менять выводы.
Конфигурация приложений в рамках анализа не изменялась.

## Основные выводы

### 1. Обновление и откат — высокий приоритет

Файлы: `sr_update_all.sh`, `sr_update.sh`, `sr_rebuild.sh`.

В `sr_update_all.sh` стек останавливается до получения кода и сборки.
`docker system prune -af` действует на весь Docker-хост и удаляет неиспользуемые
образы, которые могли понадобиться для отката. В `sr_update.sh` нет остановки
после ошибки pull/build, поэтому следующие команды могут выполниться после сбоя.

Действия:

- [ ] Сначала проверять конфигурацию, загружать и собирать образы.
- [ ] Добавить явную обработку ошибок и прекращение обновления до изменения рабочего стека.
- [ ] Использовать `up -d` без общего `down`, где это позволяет конфигурация.
- [ ] Вынести очистку Docker в отдельную обслуживающую команду.
- [ ] Сохранять версии образов и конфигурацию предыдущего релиза.
- [ ] После обновления проверять DNS и реальный трафик VPN; описать откат.

Критерий готовности: ошибка загрузки или сборки оставляет рабочий стек запущенным;
предыдущий релиз можно восстановить по документированной процедуре.

### 2. Docker socket и изоляция — высокий приоритет

Прямой socket используется OpenVPN UI, Homepage, Portainer и другими сервисами.
Доступ к Docker API может дать приложению управление хостом. Монтирование socket
с `:ro` само по себе не запрещает изменяющие запросы к API.

В `services-mine/homepage/docker-compose.yml` предусмотрен ограниченный
dockerproxy, но у Homepage одновременно оставлено прямое подключение socket.

Действия:

- [ ] Составить список потребителей socket и необходимых каждому методов API.
- [ ] Убрать прямой socket у Homepage и других приложений, которым достаточно proxy.
- [ ] Разрешать через proxy только необходимые операции.
- [ ] Разделить сети пользовательских приложений, DNS/VPN и управления.
- [ ] Проверить доступ к управляющим портам из каждого сегмента.

Критерий готовности: обычное приложение не может изменять контейнеры или читать
конфигурацию посторонних сервисов через Docker API.

### 3. Секреты и права файлов — высокий приоритет

В Compose есть стандартные пароли и токены-заглушки. Их наличие не доказывает,
что сервер использует эти значения, но допускает небезопасный запуск по умолчанию.
`services-mine/tgbot/internal/bot/accounts_store.go` сохраняет JSON с паролями
с правами `0644`; возможность чтения другими пользователями зависит также от
прав родительских каталогов.

Действия:

- [ ] Требовать настоящие секреты при старте вместо стандартных значений.
- [ ] Предусмотреть чтение секретов из файлов; использовать Docker secrets там, где это подходит.
- [ ] Сохранять файлы с паролями с правами `0600`, закрытые каталоги — `0700`.
- [ ] Исправить права уже существующих файлов и проверить резервные копии.
- [ ] Сменить стандартные значения, если они использовались на сервере.

Критерий готовности: отсутствие секрета останавливает запуск с понятной ошибкой;
посторонний пользователь хоста не читает файлы с паролями.

### 4. Внутренние API — высокий приоритет

В `services/antizapret/api/main.go` управляющие обработчики не требуют
авторизации. `/list/` принимает произвольный URL и может использоваться для
запросов во внутреннюю сеть. При этом ограничение локальных файлов через
`os.OpenRoot` уже реализовано и должно быть сохранено.
В dns-guard пустой токен отключает проверку авторизации.

Действия:

- [ ] Ограничить сетевую доступность API и добавить авторизацию управления.
- [ ] Использовать POST для операций изменения состояния.
- [ ] Ограничить источники списков с учётом перенаправлений и разрешения DNS.
- [ ] Ограничить параллельные загрузки и объём распакованных данных.
- [ ] Добавить таймауты HTTP-сервера с учётом потоковых ответов.
- [ ] Требовать токен при включённом API dns-guard.

Критерий готовности: неавторизованные изменения отклоняются; загрузчик не может
обращаться к запрещённым внутренним адресам, в том числе через redirect.

### 5. Версии, сборка и CI — средний приоритет

`versions.json` описывает преимущественно upstream-образы, а Compose использует
собственные `nmisha/*` с другими версиями. Swarm-конвертер запускается из
плавающего `xtrime/antizapret-vpn:6`. Workflow сборки запускается по изменениям
версий и нескольких служебных файлов; обычное изменение кода само по себе
не запускает этот workflow. tgbot и dns-guard отсутствуют в его матрице.

Действия:

- [ ] Ввести единый перечень релизных образов, включая собственные сервисы.
- [ ] Добавить отдельный CI проверки изменений кода на рабочих ветках и PR.
- [ ] Запускать Go/Python-тесты, проверку shell и рендеринг Compose/Swarm.
- [ ] Фиксировать версии или digest развёртываемых образов и конвертера.
- [ ] Зафиксировать поддерживаемое окружение запуска тестов.

Критерий готовности: изменение исходников запускает соответствующие проверки;
релиз однозначно определяет используемые образы.

### 6. Конфигурация AdGuard — средний приоритет

В `services/adguard/AdGuardHome.yaml` подключено много пересекающихся списков,
включая секции браузерных фильтров. Их фактическую пользу для DNS-фильтрации
следует измерить: часть синтаксиса рассчитана на обработку веб-страниц.

Действия:

- [ ] Проверить число принятых правил и ошибки каждого списка.
- [ ] Сформировать небольшой базовый набор DNS-списков.
- [ ] Оценивать дополнительные списки по ложным блокировкам, времени обновления и памяти.
- [ ] Проверить сетевую доступность DNS и необходимость ограничений клиентов.

Критерий готовности: назначение каждого включённого списка понятно;
сохранены нужные блокировки и маршрутизация, измерены затраты ресурсов.

### 7. Healthcheck и обслуживание — средний приоритет

`services/adguard/healthcheck.sh` совмещает проверку API, обновление фильтров,
изменение клиентов и очистку кэша. Ошибки обслуживания уже отделены от части
ошибок работоспособности, но обязанности остаются связанными.

Действия:

- [ ] Оставить короткую проверку DNS/API в healthcheck.
- [ ] Вынести обслуживание в отдельный цикл с повторными попытками.
- [ ] Показывать время последнего успешного обновления и возраст списков.
- [ ] Добавить внешнюю проверку DNS через VPN и доступности выходов local/world.

Критерий готовности: сбой источника списков не перезапускает работающий DNS,
а устаревшие правила видны отдельно от состояния контейнера.

### 8. Dashboard и Authelia — средний приоритет

В `services/dashboard/files/init.sh` собственная авторизация отключена;
переменные DASHBOARD_USERNAME/PASSWORD в Compose фактически не используются.
HTTPS-прокси проверяет Authelia перед приложениями, поэтому это не означает
автоматически открытый dashboard в интернете.

Действия:

- [ ] Явно закрепить доступ к dashboard только через защищённый прокси.
- [ ] Убрать неработающие настройки и ненужный CORS.
- [ ] Останавливать entrypoint при ошибке init и запускать lighttpd через exec.
- [ ] Проверить отказ в доступе при недоступной Authelia и невозможность обхода прокси.

Критерий готовности: внешние запросы проходят проверку Authelia;
ошибка генерации конфигурации не оставляет приложение работать с неполной настройкой.

## Что означают ratelimit: 0 и allowed_clients: []

- `ratelimit: 0` отключает встроенный лимит частоты DNS-запросов AdGuard.
- `allowed_clients: []` не ограничивает клиентов списком разрешённых адресов
  на уровне этой настройки AdGuard.
- `bind_hosts: [0.0.0.0]` означает прослушивание IPv4-интерфейсов внутри
  сетевого пространства контейнера, а не автоматическую публикацию на хосте.

В проверенном `services/adguard/docker-compose.yml` порт 53 не опубликован.
Эти настройки сами по себе не доказывают доступность DNS из интернета.
Доступ может появиться через override, host network, DNAT/маршрутизацию,
VPN или другой прокси. Нужно проверять фактическую конфигурацию сервера.

Открытый резолвер — это DNS-сервер, который принимает рекурсивные запросы
от произвольных внешних клиентов. Если доступа извне нет, указанные настройки
не превращают его в открытый резолвер. Если доступ есть, отсутствие ограничений
позволяет посторонним пользоваться DNS и создавать лишнюю нагрузку.

План проверки:

1. На сервере проверить итоговый Compose/Swarm, публикацию TCP/UDP 53,
   сетевой режим, firewall и DNAT. Наличие listening-порта само по себе
   недостаточно для вывода о доступности извне.
2. С устройства вне VPN и вне доверенной сети проверить обычный рекурсивный
   запрос к публичному IP: `dig @PUBLIC_IP example.org A +time=2 +tries=1`.
3. Повторить с `+tcp`; при наличии публичного IPv6 проверить и его.
4. Убедиться, что доверенный VPN-клиент продолжает успешно разрешать имена.
5. При необходимости закрыть внешний путь firewall и добавить allowed_clients,
   предварительно выяснив адреса, которые AdGuard реально видит после NAT.
6. Подбирать ratelimit по нагрузке: множество клиентов за NAT может выглядеть
   как один источник. Лимит не заменяет ограничения доступа.

Ожидаемый результат: произвольный внешний клиент не получает рекурсивного
ответа, доверенные клиенты работают. Один timeout не является окончательным
доказательством защиты: его сопоставляют с правилами сети и журналами сервера.

## Порядок выполнения

1. Обновление, сохранение предыдущего релиза и откат.
2. Docker socket, изоляция сетей, секреты и права файлов.
3. Авторизация и ограничения внутренних API.
4. Единые версии и CI с воспроизводимым тестовым окружением.
5. Упрощение AdGuard, разделение healthcheck и обслуживания, наблюдаемость.
6. Проверка восстановления из резервной копии конфигурации и состояния.

Каждый этап выполнять отдельным изменением с проверкой штатного поведения
и соответствующего сценария отказа. Сетевые ограничения вводить после
инвентаризации реальных потоков, чтобы не оборвать DNS и управление VPN.
