# Диагностика TLS YouTube

Наблюдения от 1 ноября 2026 года. Это диагностические скрипты и план интеграции,
а не включённое исправление серверной конфигурации.

## Что удалось воспроизвести

На компьютере Chrome получает HTTP 200 через `az-local` по TCP/HTTP/2.
QUIC отключён только для тестового экземпляра, профиль новый, сертификат
проверяется. NetLog сообщает TLS 1.3 и `encrypted_client_hello: false`.
Имя `www.youtube.com` видно в захваченном ClientHello.

Системный curl на том же адресе `14.16.0.50:443` устанавливает TCP, отправляет
ClientHello, но не получает ServerHello до таймаута. Размер TLS-записи curl —
325 байт, Chrome — около 2 КБ. Отличаются группы обмена ключами, набор и порядок
расширений. Увеличение ClientHello curl одним padding не устранило проблему.

Без запуска Chrome библиотека curl_cffi 0.17.0 с профилем `chrome152` также
получила HTTP 200. Однако результат неустойчив: 1 из 2 попыток. В этих же двух
раундах обычный профиль BoringSSL и системный curl не получили ответа.
Вариант Chrome без GREASE получил 200 в обеих попытках, без ECH — в одной,
без постквантовой группы — ни в одной. Это маленькая выборка, а порядок TLS-
расширений может меняться: объявлять какое-либо расширение причиной нельзя.
Успех при выключенном ECH дополнительно исключает его необходимость.

Более полезный для шлюза эксперимент: обычный curl через loopback TCP-relay,
который оставляет TLS-байты неизменными, но отправляет ClientHello двумя
частями внутри SNI, после `www.`. При задержке между записями 40 мс:

| Место теста | Без разделения | С разделением SNI |
| --- | --- | --- |
| Компьютер → `14.16.0.50` → local | 0/3 HTTP 200 | 3/3 HTTP 200 |
| Московский сервер → `142.251.153.4` | 0/3 HTTP 200 | 1/3 HTTP 200 |

На компьютере без задержки разделение дало 1/2 успешных попыток, контроль —
0/2. Loopback-relay создаёт новое исходящее TCP-соединение, но не завершает TLS.
Границы вызовов `sendall` не гарантируют границы сетевых пакетов. Это ещё
не проверка стратегии nfqws2 и не гарантия работы для LG или всех клиентов.

Результат согласуется с чувствительностью фильтрации к TLS-профилю и
сегментации. Точный алгоритм и место фильтрации не установлены.

## Как повторить

Реальный Chrome и системный curl, один IP, QUIC выключен:

```sh
python3 scripts/compare-chrome-curl.py --ip 14.16.0.50
```

Клиенты с разными TLS-профилями без Chrome, зависимости в отдельном venv:

```sh
python3 -m venv /tmp/youtube-tls-lab-venv
/tmp/youtube-tls-lab-venv/bin/pip install curl_cffi==0.17.0
/tmp/youtube-tls-lab-venv/bin/python scripts/compare-tls-profiles.py \
  --ip 14.16.0.50 --rounds 3 --output /tmp/youtube-tls-profiles.json
```

Обычный curl и разделение SNI, только стандартная библиотека Python:

```sh
python3 scripts/test-tls-split.py \
  --ip 14.16.0.50 --rounds 3 --output /tmp/youtube-tls-split.json
```

Адреса `14.16.*` являются локальными синтетическими адресами этой установки,
а не публичными адресами YouTube. На другой установке опустите `--ip`.
IP одного домена не следует использовать для другого домена без проверки.
Скрипты не проверяют воспроизведение видео, авторизацию и QUIC.

## Как применять в проекте

curl_cffi подходит для диагностического клиента. Он не меняет TLS-профиль
транзитного телевизора. Подменять ClientHello клиента на Chrome в шлюзе нельзя:
проверка TLS использует хеш сообщений рукопожатия. Смена ClientHello нарушает
его целостность. Прокси, завершающий TLS, потребовал бы доверенного сертификата
на клиентах и отдельной проверки совместимости приложений.

Подходящий существующий компонент — `zapret2/nfqws2` внутри контейнера выхода.
В `services/antizapret/init.sh` уже есть запуск через `ZAPRET_ENABLED`, а
`services/antizapret/root/zapret2/config.default` задаёт `NFQWS2_OPT`.
На проверенном московском сервере установлен nfqws2 v1.0.2, обработка отключена.
Функция `multisplit` в этой версии присутствует; текущая конфигурация по
умолчанию использует fake, что не эквивалентно успешному эксперименту.

План интеграции:

1. На изолированном тестовом выходе подобрать стратегию TCP-сегментации вокруг
   SNI (`multisplit`, при необходимости `multidisorder`) с учётом реального
   MTU, offload и точки обработки относительно DNAT/SNAT. Не переносить
   числовую позицию 248 из Mac: ClientHello у каждого клиента свой.
2. Ограничить профиль доменами YouTube: `youtube.com`, `googlevideo.com`,
   `ytimg.com`, `ggpht.com`, `youtubei.googleapis.com`. Для доменных фильтров
   убедиться, что nfqws2 видит и собирает ClientHello при транзите.
3. Проверять по отдельности TCP и UDP/443. TCP-стратегия не исправляет QUIC;
   не блокировать UDP глобально ради перехода на TCP.
4. Сравнить контроль/обработку на реальных транзитных клиентах: curl с TLS 1.2
   и 1.3, Chrome, планшет, LG. Проверить холодный запуск LG, вход в аккаунт,
   миниатюры и реальные CDN-видеопотоки, а не только главную страницу.
5. После устойчивых повторов оформить отдельный подключаемый профиль zapret2,
   оставить возможность отката и описать включение. Сохранить маршрут YouTube
   через local, если требуется российский выходной IP.

Простое включение текущего `ZAPRET_ENABLED=1` не является подтверждённым
исправлением. Стратегия ещё не испытана в NFQUEUE и на LG. Работающие настройки
серверов во время исследования не менялись.
