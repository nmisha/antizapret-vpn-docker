# План перехода с auth proxy на OIDC

Статус: план, OIDC на сервере не включён. Сейчас используется
`reverse-proxy-guard`; провайдер OIDC в Authelia ещё не настроен.

Целевая схема: каждый пользователь входит через Authelia в собственный профиль
2FAuth. Группа `twofauth_users` разрешает вход, а владельцы записей отдельно
выдают доступ к кодам средствами 2FAuth. Группы Authelia не становятся группами
записей 2FAuth и не выдают административную роль автоматически.

## Порядок настройки

1. Сохранить согласованную резервную копию SQLite 2FAuth, постоянный `APP_KEY`,
   конфигурацию и данные Authelia. Зафиксировать пользователей, владельцев
   записей и расшаривания на момент миграции.
2. Настроить OIDC provider Authelia: постоянные ключи подписи JWKS и необходимые
   секреты провайдера. Зарегистрировать конфиденциальный клиент 2FAuth с новым
   client secret. Секреты не хранить в Git.
3. Настроить клиент: scopes `openid`, `profile`, `email`, метод
   `client_secret_post`, redirect URI
   `https://twof.auth.marina.2bd.net/socialite/callback/openid`.
   Использовать отдельную OIDC authorization policy: по умолчанию deny,
   разрешение `one_factor` только группе `twofauth_users`. Правила обычного
   `access_control` сами по себе не ограничивают выдачу OIDC-токенов.
4. В окружении 2FAuth настроить `OPENID_AUTHORIZE_URL`, `OPENID_TOKEN_URL`,
   `OPENID_USERINFO_URL`, `OPENID_CLIENT_ID`, `OPENID_CLIENT_SECRET` и проверку
   TLS. URL берутся у фактического портала Authelia; пути соответственно
   `/api/oidc/authorization`, `/api/oidc/token`, `/api/oidc/userinfo`.
   Переключить guard с `reverse-proxy-guard` на поддерживаемый обычный режим
   приложения после проверки конфигурации установленной версии.
5. Заранее подготовить привязки существующих пользователей. Установленный
   `SocialiteController` ищет пару `oauth_provider=openid` и `oauth_id`,
   полученный из идентификатора провайдера. Он НЕ объединяет аккаунты по email:
   при занятом email возвращает `sso_email_already_used`. Получить фактический
   `sub` каждого пользователя именно для этого клиента, проверить соответствие
   и привязать к существующему ID пользователя 2FAuth. Не подставлять логин
   вместо `sub` и не удалять старые аккаунты ради обхода конфликта email.
   Контроллер также обновляет имя и email при входе — учесть это при откате
   к сопоставлению по логину через auth proxy.
6. Убрать для этого сайта подмену на `chatgpt`. После проверки OIDC убрать
   дополнительный forward-auth перед 2FAuth, если он больше не нужен:
   вход будет обеспечивать само приложение. Сохранить HTTPS и закрытый порт
   контейнера. Изменить источник конфигурации Caddy, а не только autosave.json.
7. Проверить вход администратора и обычного пользователя, запрет входа без
   группы, сохранение владения и расшариваний, выход и повторный вход.
   Проверить настройки регистрации SSO и локального входа. Ограничение OIDC
   не обязательно немедленно завершает уже созданную сессию 2FAuth — отдельно
   проверить отзыв доступа и сроки сессий.

## Особенности текущей установки

- Общую учётку `chatgpt` нельзя автоматически связать сразу с несколькими
  OIDC-пользователями. Её записи нужно оставить у владельца с расшариванием
  либо передать выбранному личному пользователю.
- Передача владения в установленном интерфейсе требует локальный пароль.
  OIDC сам по себе этого требования не устраняет; новым SSO-пользователям
  приложение генерирует случайный локальный пароль. Этот сценарий нужно
  отдельно проверить до миграции.
- Для пробного запуска использовать отдельную копию приложения и базы:
  не подключать два экземпляра с разными режимами входа к рабочей SQLite.
- Для отката сохранить не только настройки guard/Caddy, но и исходные
  идентификаторы, имена и привязки пользователей. Полный откат базы после
  новых изменений может потерять эти изменения.
