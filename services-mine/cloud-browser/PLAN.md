# Cloud browser: контекст и план

Документ для продолжения работы в новой сессии. Состояние на 20 сентября 2026 года. Реализация пока не менялась: это результаты анализа и план.

## Цель

Дать доступ к Chromium, работающему на сервере, через обычный браузер. Для первого прототипа выбран образ `lscr.io/linuxserver/chromium` с Selkies: один постоянный контейнер, один домен, сохранение профиля в `/config`. Собственный frontend и менеджер сессий на первом этапе не нужны.

```text
Пользователь → HTTPS-домен → Caddy + Authelia → Chromium:3000 → Selkies → Chromium
                                                └→ постоянный /config
```

## Что уже есть в репозитории

- `services-mine/cloud-browser/docker-compose.yml` содержит сервисы `chromium` и `firefox`. У Chromium есть `hostname: chromium.antizapret`, `shm_size: 2gb`, привязка `$PWD/config-mine/chromium:/config` и размещение на узле `local` в Swarm.
- Этот файл сам по себе не включает сервис в основной стек. В просмотренных основных Compose-файлах и документации подключения `cloud-browser` нет. Перед запуском нужно проверить **эффективный override на целевом компьютере**: локальные файлы конфигурации могут отсутствовать в Git.
- Сервис `https` проекта использует Caddy и умеет публиковать приложения по домену через `PROXY_VHOST_N` с проверкой Authelia. Описание механизма: `services/https/README.md`. Для домена при SNI-маршрутизации также нужен соответствующий `SNI_ROUTE_N`.
- `firefox` для первого прототипа не нужен. Его наличие в файле не означает, что его надо запускать.

## Важные технические условия

- При TLS на Caddy проксировать на **HTTP-порт 3000** контейнера; порт 3001 предназначен для прямого HTTPS-доступа с самоподписанным сертификатом. Пользователь должен открывать сайт по HTTPS.
- Поток Selkies использует WebSocket. При проверке важно убедиться, что работает изображение и соединение держится, а не только загружается страница. Если поток обрывается, проверить proxy/WebSocket и тайм-ауты.
- Не публиковать порт контейнера напрямую в Интернет. Образ по умолчанию не требует входа; доступ к GUI может дать терминал и root внутри контейнера. Нужны Authelia и продуманная сетевая доступность контейнера.
- Один постоянный контейнер означает **общую сессию и общий профиль** для всех допущенных пользователей. Это приемлемо лишь для первого личного прототипа.
- Привязка `/config` сохраняет настройки, вкладки и данные браузера. Для будущих одноразовых сессий общий `/config` использовать нельзя.
- В текущей заготовке указан `image: ...:latest` и одновременно `build:`. Перед внедрением решить, нужен ли локальный build: для стандартного образа достаточно `image`.
- Для Swarm `docker stack deploy` не собирает образы; bind mount `/config` должен существовать на узле, где запускается контейнер.

## План

1. На целевом компьютере проверить эффективные Compose/Swarm override, существующие `PROXY_VHOST_N`, `SNI_ROUTE_N`, домен браузера и правила доступа Authelia. Не перезаписывать локальную конфигурацию вслепую.
2. Подключить **только Chromium** к эффективному стеку. Сохранить постоянный `/config`, не открывать наружу `3000`/`3001`; убедиться, что Caddy и Chromium находятся в доступной друг другу Docker-сети.
3. Настроить HTTPS-домен в существующем Caddy: upstream `chromium.antizapret:3000`, проверка через Authelia, необходимый SNI-маршрут и DNS. Проверить, что WebSocket проходит через proxy.
4. Запустить прототип и проверить: вход; изображение и управление; переходы по сайтам; переподключение; сохранение данных после перезапуска; доступ без авторизации; логи при разрыве сессии.
5. После работающего прототипа отдельно спроектировать создание контейнера на пользователя/сессию, временный профиль, лимиты CPU/RAM, автоматическую уборку и отдельный сетевой выход или VPN. Для этого понадобится сервис управления сессиями; один статический Compose этого не обеспечивает.
6. Собственный frontend с адресной строкой добавлять после проверки жизненного цикла сессий. Он не должен подменять серверную авторизацию и изоляцию.
