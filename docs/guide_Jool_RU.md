# Подготовка хоста для IPv6-выхода через Jool SIIT

Статус: экспериментальная интеграция реализована и проверена локально с Jool.
На целевых серверах она не развёрнута. Установка модуля сама по себе IPv6-выход
не включает. Команды ниже выполняет оператор на каждом Linux-хосте, где может
работать `az-local` или `az-world`, а не внутри контейнера.

Основной вариант проекта: Jool SIIT переводит пакеты IPv4↔IPv6, Linux NAT66
объединяет исходящие соединения клиентов на одном IPv6-адресе выхода.
Обычный stateful NAT64 `jool` вместо SIIT `jool_siit` здесь не нужен.

## 1. Проверить хост

```sh
cat /etc/os-release
uname -r
uname -m
ip -6 addr show scope global
ip -6 route show default
command -v mokutil >/dev/null && mokutil --sb-state
```

Команды установки ниже предназначены для Ubuntu/Debian с APT и возможностью
загружать модули ядра. Для LXC/OpenVZ модуль устанавливается на реальном хосте
виртуализации; доступ root внутри гостевой среды этого не гарантирует.

Выбранная исходная версия — **4.1.15**, одинаковая для модуля и будущего клиента
в образе. По [таблице совместимости Jool](https://nicmx.github.io/Jool/en/intro-jool.html)
она поддерживает mainline-ядра 5.15–6.18. Дистрибутивные backport-патчи всё равно
требуют проверки сборки. Для другого ядра сначала выбрать совместимый релиз,
затем согласовать его с версией клиента в образе. Ветка `main` не используется
как автоматически обновляемая зависимость.

## 2. Выбрать один способ установки

Не смешивать пакетную и исходную установки Jool. Предварительно проверить:

```sh
dpkg-query -W jool-dkms jool-tools 2>/dev/null
dkms status
command -v jool_siit
modinfo jool_siit 2>/dev/null
```

### Вариант A: пакеты дистрибутива

```sh
sudo apt-get update
apt-cache policy jool-dkms jool-tools
sudo apt-get install dkms build-essential "linux-headers-$(uname -r)"
```

Если обе версии пакетов подходят ядру и согласованы с будущим образом проекта:

```sh
sudo apt-get install jool-dkms jool-tools
dpkg-query -W -f='${Package} ${Version}\n' jool-dkms jool-tools
```

Доступная версия зависит от выпуска ОС и подключённых репозиториев. Не
подключать Debian testing/unstable или сторонний PPA только ради этой инструкции.
Если версия слишком старая для ядра, использовать вариант B вместо варианта A.

### Вариант B: фиксированный релиз через DKMS

Подходит для чистой установки без существующего пакетного Jool. Если Jool уже
используется, сначала спланировать замену в окно обслуживания.

```sh
sudo apt-get update
sudo apt-get install dkms build-essential pkg-config curl ca-certificates \
    "linux-headers-$(uname -r)" libnl-genl-3-dev libxtables-dev
mkdir -p "$HOME/jool-build"
cd "$HOME/jool-build"
curl -fL --retry 3 -o jool-4.1.15.tar.gz \
    https://github.com/NICMx/Jool/releases/download/v4.1.15/jool-4.1.15.tar.gz
tar -xzf jool-4.1.15.tar.gz
sudo dkms install ./jool-4.1.15/
```

Модуль и управляющий клиент собираются отдельно. Клиент на хосте полезен для
диагностики; при работе проекта его копия будет также находиться в контейнере:

```sh
cd "$HOME/jool-build/jool-4.1.15"
./configure
make -j2
sudo make install
sudo ldconfig
```

Сохранить каталог сборки для последующего удаления клиента. Проверить, что
`command -v jool_siit` указывает на ожидаемую установку.

## 3. Проверить загрузку и включить автозагрузку

```sh
sudo modprobe jool_siit
modinfo -F version jool_siit
modinfo -F vermagic jool_siit
lsmod | grep -E '^jool_(siit|common)\b'
dkms status
jool_siit --version
sudo jool_siit instance display
```

Ожидается: DKMS сообщает `installed` для текущего ядра, модуль загружается,
клиент читает список экземпляров. Пустой список допустим. Не создавать рабочий
экземпляр в host namespace: им будет управлять контейнер проекта.
`modinfo` показывает модуль на диске; если он уже был загружен до обновления,
это не подтверждает обновление работающего модуля.

После успешной проверки:

```sh
printf '%s\n' jool_siit | sudo tee /etc/modules-load.d/jool-siit.conf
```

### Если модуль не загрузился

```sh
sudo journalctl -k -n 100 --no-pager
dkms status
ls -ld "/lib/modules/$(uname -r)/build"
```

- `Module not found`: проверить DKMS, установленное ядро и заголовки.
- Ошибка сборки: изучить `make.log` в `/var/lib/dkms/jool/`, сверить совместимость.
- `Key was rejected`/`Required key not available`: при Secure Boot подписать
  модуль и зарегистрировать ключ согласно процедуре своего дистрибутива.
  Например, для Ubuntu использовать [официальную инструкцию по DKMS/MOK](https://wiki.ubuntu.com/UEFI/SecureBoot/DKMS).
  Регистрация может потребовать перезагрузки и доступа к консоли VPS.
- `Unknown symbol`/`Invalid module format`: проверить, что модуль собран для
  текущего ядра и не смешаны разные установки Jool.

## 4. Проверить IPv6 и сетевые предпосылки

```sh
ip -6 addr show scope global
ip -6 route show default
sysctl net.ipv6.conf.all.disable_ipv6
sysctl net.ipv6.conf.all.forwarding
sudo ip6tables -t nat -S
```

Проверить внешнюю IPv6-связность отдельно, например:

```sh
ping -6 -c 3 2606:4700:4700::1111
```

Один неудачный ping не доказывает отсутствие IPv6: ICMP echo может фильтроваться.
Для проверки TCP нужен доступный IPv6-сервер с известным портом.

Наличие IPv6 на хосте не означает, что он доступен в сетевом пространстве
контейнера. Окончательная реализация должна проверить адрес, маршрут,
forwarding и NAT66 именно там, где установлен экземпляр Jool. Выбранная схема дополнительного macvlan описана ниже;
сам overlay остаётся IPv4-only.

Не включать forwarding на хосте вслепую: при получении маршрута через RA это
может изменить приём RA. Если выбранная схема требует host forwarding,
сохранить маршрут и согласовать `accept_ra=2` только на интерфейсе, который
действительно получает RA. Провайдер может использовать статический маршрут.
Не заменять правила firewall и не отключать проверку ICMPv6 PTB.

Контейнеру Jool нужен NET_ADMIN, но не SYS_MODULE, не privileged и не TUN.
Требования WARP к TUN от этой функции не меняются. Модуль устанавливается на
всех узлах, подходящих под placement constraints выходов Swarm.

## 5. После обновления ядра

До перезагрузки убедиться, что DKMS собрал Jool для нового ядра. После
перезагрузки повторить проверки из раздела 3 и проверить IPv6. Обновление файла
модуля или рестарт контейнера не заменяет уже загруженный модуль. Для замены
использовать перезагрузку в окно обслуживания либо выгрузку после остановки
всех использующих его контейнеров. Не выгружать модуль при работающем выходе.

## 6. Откат

Сначала отключить будущую NAT46-функцию и остановить использующие Jool
контейнеры. Убедиться, что модуль не нужен другим сервисам.

```sh
sudo rm /etc/modules-load.d/jool-siit.conf
sudo modprobe -r jool_siit
```

Для пакетного варианта:

```sh
sudo apt-get remove jool-dkms jool-tools
```

Для исходного клиента:

```sh
cd "$HOME/jool-build/jool-4.1.15"
sudo make uninstall
sudo ldconfig
dkms status
```

Затем удалить DKMS-запись командой `sudo dkms remove jool/ВЕРСИЯ --all`, подставив
точную версию из `dkms status`. `jool_common` выгружать только если его больше
не используют другие экземпляры Jool. Возврат к IPv4 требует также очистки
клиентского DNS-кэша, содержащего старые NAT46-адреса.

## Как разделены Jool, NAT66 и DNS

Jool SIIT меняет семейство пакета: IPv4 становится IPv6, обратный пакет — IPv4.
EAMT задаёт соответствие синтетического IPv4 конкретному IPv6 назначения.
SIIT не объединяет клиентов на одном адресе через трансляцию портов.

В выбранной схеме IPv4 каждого клиента кодируется в отдельный внутренний IPv6.
NAT66 заменяет эти исходящие IPv6 одним адресом выхода и ведёт conntrack для
обратных пакетов. Если порты совпадают, один из них может измениться. Таким
образом, Jool решает задачу семейства адресов, NAT66 — общего исходящего адреса.
При наличии маршрутизируемого IPv6-префикса для клиентов возможна другая схема
без NAT66, но она не входит в текущую реализацию.

DNS-интеграция означает изменение существующего dnsmap, а не замену DNS-стека:
для A-запроса выбранного домена получить AAAA внутри выбранного выхода,
выделить обычный синтетический IPv4 из общего пула, установить соответствие
в Jool и только после подтверждения вернуть клиенту A. Остальные запросы
продолжают идти существующим путём. Клиенты не получают IPv6-адреса.

## Ограничения и особенности первой версии

- Обычные правила определяют direct/local/world. IPv6 include/exclude
  выбранного выхода выбирают семейство и не переносят домен на другой выход.
- Исключение IPv6 отменяет только IPv6-override. ASN сам по себе IPv6 не включает.
- Выбран IPv6, но нет пригодного AAAA или не удалось установить mapping:
  SERVFAIL. Автоматического перехода на IPv4 при ошибке DNS или соединения нет.
- Клиенты остаются IPv4-only. HTTPS/SVCB, DNSSEC-флаги и CNAME должны получить
  отдельные проверки; синтезированный A нельзя представлять как исходный
  DNSSEC-подписанный ответ. UDP echo не считается проверкой реального QUIC.
- Для IPv4 DNAT и IPv6 EAMT используется один пул. При исчерпании новые
  соответствия отклоняются, существующие не очищаются автоматически.
- Подтверждённое добавление mapping требуется до DNS-ответа. После неоднозначной
  ошибки адрес нельзя переиспользовать, пока состояние backend не сверено.
- DNAT и EAMT — разные подсистемы: общей атомарной транзакции между ними нет.
- Предусмотрено восстановление после штатной остановки. Периодические снимки
  и сохранение последних изменений после SIGKILL/сбоя хоста не входят в первую версию.
- NAT66 использует conntrack и может менять исходный порт. Сохранение mapping
  не сохраняет TCP/UDP-состояние NAT66: восстановление адресов после рестарта
  не гарантирует продолжение уже открытых соединений.
- IPv6-связность должна быть проверена в namespace выхода. Для Swarm способ
  подключения IPv6 пока не подтверждён; одного модуля на хосте недостаточно.
- Jool может переводить пакеты с обходом обычного FORWARD hook. Порядок
  firewall, DNAT, NAT66 и обратной трансляции требует проверки на стенде.
  См. [описание hooks Jool](https://nicmx.github.io/Jool/en/intro-jool.html).
- Локально проверены Jool + host NAT66, TCP, UDP/443, QUIC/443 и PTB/MTU,
  а также маршрутизируемый режим без NAT66. Полный production CoreDNS/AdGuard,
  реальный VPN ingress и связь между двумя узлами Swarm в этом стенде не
  проверены: тестовый Swarm имеет один узел, DoH upstream контролируемый.

## Результат чтения целевого окружения — 2026-11-06

Оба узла: Ubuntu 24.04.5, ядро 6.8.0-147-generic, Docker 29.9.2.
Заголовки текущего ядра присутствуют, Jool не установлен. В APT доступен
4.1.11-1ubuntu0.1; это не выбранный исходный релиз 4.1.15, версии автоматически
не подменять.

Сеть `antizapret6-swarm_default`: encrypted overlay, IPv6 выключен,
10.200.0.0/24, заданный MTU 1476. На local интерфейс overlay внутри выхода имеет
MTU 1400. `docker_gwbridge` также IPv4-only: local 172.18.0.0/16,
world 172.20.0.0/16. Оба выхода используют IPv4 default route через eth1;
в namespace выходов глобальные IPv6 и IPv6-маршруты отсутствуют,
IPv6 forwarding выключен.

Local: публичный IPv6 /128 на eth0, default route помечен proto ra,
host IPv6 forwarding=0, accept_ra eth0=0. Из одного этого снимка нельзя
определить механизм продления маршрута; при изменении forwarding нужна проверка.
World: публичный IPv6 /64 на ens3, статический default route,
host IPv6 forwarding=1. Уже работает отдельный IPv6 bridge с ULA и host
MASQUERADE для другого стека: его правила не изменять и подсеть не переиспользовать.
Назначенный /64 сам по себе не подтверждает делегированный routed prefix.

Вывод: текущий overlay не предоставляет IPv6-выход контейнерам. Новая схема
должна явно организовать этот путь; host IPv6 не следует считать готовностью
NAT46 внутри контейнера. Все проверки были read-only, без загрузки модулей,
перезапуска контейнеров и изменения сетей.

## Реализованная схема и включение в Swarm

Пакетный стенд уточнил архитектуру: **NAT66 выполняется на хосте, после Jool**.
В проверенной конфигурации правило NAT66 в том же namespace, что Jool, не
обрабатывает сгенерированные им пакеты. Не переносить правило MASQUERADE
из TAYGA-стенда в контейнер Jool.

```text
IPv4 VPN -> az-* в overlay -> Jool SIIT -> дополнительный macvlan
    -> macvlan-shim хоста -> host NAT66 -> публичный IPv6
```

Дополнительная сеть работает на внутреннем dummy-интерфейсе хоста. MAC-адреса
контейнеров не выходят в сеть провайдера. Overlay остаётся IPv4-only.
IPvlan в этом стенде не доставлял обратные пакеты префикса клиентов в Jool;
используется macvlan bridge mode.

Один хост должен обслуживать только один выход с этой конфигурацией сети.
Зарезервирован один IPv4 и один IPv6 адрес задачи. Реплика — одна, обновление
**stop-first**; перекрывающиеся задачи и start-first не поддерживаются.
Placement local/world должен разводить выходы по разным хостам.

### Подготовить сеть на каждом хосте

После установки и загрузки Jool проверить IPv6 forwarding и приём RA. На local
он был выключен. Для данной схемы нужен `net.ipv6.conf.all.forwarding=1` на
хосте, сохранённый в sysctl.d. Если default route получается через RA,
обеспечить его продление при forwarding (обычно `accept_ra=2` на конкретном
uplink, с учётом конфигурации systemd-networkd/провайдера). Проверить внешний
IPv6 до и после изменения. Скрипт ниже не меняет forwarding автоматически.

Создать `/etc/default/antizapret-nat46` на local:

```sh
NAT46_SOURCE_PREFIX=fd46:64::/96
NAT46_WAN_INTERFACE=eth0
NAT46_NAT66_ENABLED=1
```

На world:

```sh
NAT46_SOURCE_PREFIX=fd46:65::/96
NAT46_WAN_INTERFACE=ens3
NAT46_NAT66_ENABLED=1
```

Проверить отсутствие пересечений с существующими сетями: новая сеть использует
172.31.46.0/29 и fd46:ee::/64. Эти значения одинаковы на разных хостах,
поскольку dummy/macvlan-сегменты между хостами не соединяются. Они не должны
совпадать с VPN-подсетями и существующими маршрутами.

Установить скрипт из репозитория и выполнить на **обоих** хостах:

```sh
sudo install -m 0755 scripts/nat46-egress-host.sh /usr/local/sbin/antizapret-nat46-egress
sudo /usr/local/sbin/antizapret-nat46-egress apply
```

Он создаёт dummy `az46-parent`, shim `az46-shim`, маршрут клиентского IPv6
префикса, config-only сеть Docker и собственные цепочки NAT/firewall.
Существующие правила другого IPv6 bridge не заменяет. При несовпадении
существующей config-only сети останавливается с ошибкой.

На manager **один раз**, после подготовки обоих хостов:

```sh
docker network create --driver macvlan --scope swarm \
    --config-from antizapret-nat46-egress-config antizapret-nat46-egress
```

Config-only сеть с одинаковым именем должна существовать на каждом допустимом
хосте. При появлении нового узла сначала подготовить его, затем разрешать
размещение выхода.

Для восстановления shim, маршрутов и правил после reboot/Docker restart
создать `/etc/systemd/system/antizapret-nat46-egress.service`:

```ini
[Unit]
Description=AntiZapret NAT46 host egress
Wants=network-online.target
After=network-online.target docker.service
Requires=docker.service
PartOf=docker.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/antizapret-nat46-egress apply
RemainAfterExit=yes

[Install]
WantedBy=docker.service
```

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now antizapret-nat46-egress.service
```

На старте Docker задача может первоначально не запуститься до появления parent;
Swarm должен повторить запуск после подготовки сети. Проверить convergence,
журнал unit и маршрут после первой перезагрузки в окно обслуживания.

### Собрать образ и подключить override

Пересобрать образ из текущего репозитория и указать свой опубликованный тег
для обоих выходов через обязательную переменную `NAT46_IMAGE`. Override
не публикует образ; при отсутствии переменной генерация останавливается,
чтобы случайно не развернуть старый образ без NAT46.
Добавить его **после** `compose.swarm.yml` к существующей цепочке Compose-файлов
при генерации Swarm stack через используемый проектом compose2swarm.

Пример сборки (заменить registry/name/tag своими):

```sh
export NAT46_IMAGE=registry.example.com/your-name/antizapret-vpn:nat46-1
export NAT46_ADGUARD_IMAGE=registry.example.com/your-name/antizapret-adguard:nat46-1
docker build -t "$NAT46_IMAGE" services/antizapret
docker push "$NAT46_IMAGE"
docker build --build-arg ROUTES_IMAGE="$NAT46_IMAGE" -t "$NAT46_ADGUARD_IMAGE" services/adguard
docker push "$NAT46_ADGUARD_IMAGE"
```

Перед генерацией проверить в той же shell с экспортированными NAT46_IMAGE и NAT46_ADGUARD_IMAGE:

```sh
docker compose -f docker-compose.yml -f compose.swarm.yml -f compose.nat46.yml config
```

Override включает NAT46 и сохранение mappings, подключает дополнительную сеть,
сохраняя overlay и placement. Проверить в итоговом stack, что cap_add NET_ADMIN,
оба подключения и переменные NAT46 сохранились.

IPv4 gateway по умолчанию в override соответствует прочитанным узлам:
local 172.18.0.1, world 172.20.0.1. Перепроверить при деплое. Swarm может выбрать
macvlan как IPv4 default route, поэтому init явно возвращает маршрут через
`NAT46_IPV4_GATEWAY`. `DOCKER_SUBNET` задаётся явно как overlay 10.200.0.0/24,
поскольку при нескольких сетях нельзя считать eth0 интерфейсом overlay.

`NAT46_CLIENT_SUBNETS` содержит разделённые `;` IPv4-подсети источников;
по умолчанию override включает 10.1.164.0/22 и 10.200.0.0/24. При других VPN
подсетях обновить значение. Источник без EAMT-перевода не сможет использовать
NAT46. Общий pool6 намеренно не включается: это сохраняет обычный IPv4 DNAT.

### Доменные списки и поведение

В custom-каталоге каждого выхода:

```text
include-hosts-ipv6-custom.txt
exclude-hosts-ipv6-custom.txt
```

Пример world: добавить `gemini.google.com` в обычный world-список маршрутизации
и в IPv6 include на world. Только IPv6 include не выбирает world/local.
IPv6 exclude отменяет семейство IPv6 и возвращает обычный IPv4-путь.

Одна строка — hostname с поддоменами или `/regex/`; пустые строки и комментарии
с `#` игнорируются. Regex здесь выполняет Python `re`, поэтому GNU ERE/POSIX
конструкции из старых исключений нельзя переносить без проверки.
Списки перечитываются по mtime/размеру при запросе, без рестарта. Некорректный
файл приводит к SERVFAIL при обработке A на выходе, пока файл не исправлен.

Клиентам не выдаются AAAA/HTTPS из dnsmap, как и прежде. IPv6 CNAME-цепочка
превращается в A исходного имени; AD-флаг и подписи AAAA не переносятся.
Отсутствие AAAA/ошибка mapping означает SERVFAIL; IPv4 fallback отсутствует.

### Выключить NAT66

Это требует **маршрутизируемого публичного /96**, не просто адреса /64 на
интерфейсе. Подставить его в NAT46_SOURCE_PREFIX хоста и соответствующий
NAT46_LOCAL_SOURCE_PREFIX/NAT46_WORLD_SOURCE_PREFIX при генерации stack.
На хосте задать `NAT46_NAT66_ENABLED=0` и
`NAT46_ROUTED_PREFIX_CONFIRMED=1`, повторно применить host script. В stack
тоже установить `NAT46_NAT66_ENABLED=0`.

Маршрут провайдера должен доставлять этот /96 на хост, а host route — в Jool.
Применять изменение с остановкой выхода и переподключением клиентов, поскольку
меняется источник соединений. Режим с NAT66 остаётся первоначальным вариантом.

### Отключение функции и удаление сети

Сначала убрать IPv6 include и очистить клиентские DNS-кэши либо дождаться
истечения ранее выданных ответов. Отключить NAT46, убрать дополнительную сеть
из stack и дождаться удаления задач, использовавших её. Затем отключить unit,
удалить внешнюю сеть на manager и config-only сети на узлах. Только после
этого удалить собственные jumps/цепочки AZ_NAT46, AZ_NAT46_FWD, маршрут /96,
az46-shim и az46-parent. Не очищать таблицы NAT/firewall целиком.

Остановка и повторное создание namespace теряют conntrack; восстановление
synthetic mappings сохраняет назначения старых DNS-ответов, а не TCP-сессии.


### Дополнительные границы поддержки

Jool netfilter обрабатывает входящие пакеты. Соединения к NAT46-адресам,
созданные процессами непосредственно внутри самого `az-*`, не поддерживаются
этой схемой; клиенты и отдельные proxy-контейнеры должны приходить на выход по
сети. Их IPv4-подсети должны входить в NAT46_CLIENT_SUBNETS. Не включать в них
/32 и синтетические диапазоны.

Совместная работа с WARP и правилами IPv6 DPI/zapret отдельно не проверялась.
Первоначальная проверенная конфигурация использует WARP_ENABLED=0 и
ZAPRET_ENABLED=0, как на прочитанных выходах. No-NAT66 проверен на изолированном
маршрутизируемом префиксе, а не на сети провайдера.

Данные тестов и воспроизведение: [локальный стенд](../scripts-diag/nat46/README.md).
Полная сборка образа и проверка сгенерированного stack — локальные; образ не
опубликован, серверные контейнеры не изменены.

Нагрузочная проверка больших EAMT не выполнялась. Первая версия использует
Jool CLI и чтение таблицы для подтверждения новых соответствий; при большом
числе IPv6-назначений время добавления/восстановления нужно измерить отдельно.


### AdGuard и внутренние AAAA

Нужен также пересобранный AdGuard-образ через `NAT46_ADGUARD_IMAGE`.
Исходная настройка `aaaa_disabled: true` блокирует даже внутренние AAAA.
При NAT46_ENABLED=1 entrypoint отключает этот глобальный запрет и добавляет
правило пустого AAAA-ответа для всех, кроме persistent clients с именами
az-local, az-world и az-resolver. Их прямые upstreams сохраняются, поэтому
внутренний AAAA не возвращается через CoreDNS в dnsmap.

Обычные клиенты и coredns по-прежнему не получают AAAA. При выключении NAT46
удаляется только это управляемое правило и возвращается глобальный запрет AAAA.
Правила выбора выхода и глобальные исключения этим правилом не отменяются.
Синтаксис client/dnstype/dnsrewrite проверяется отдельным тестом настоящего
AdGuard, не только mock-сервером DoH.

Перед возвратом к старому AdGuard-образу сначала запустить новый образ с
NAT46_ENABLED=0: он восстановит глобальный запрет AAAA и уберёт своё правило.
Иначе старый entrypoint не выполнит эту миграцию сохранённого конфига.

Сводка выполненных проверок: [RESULTS.md](../scripts-diag/nat46/RESULTS.md).
